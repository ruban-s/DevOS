## The point

The whole point is **euphoric surprise**: the principal got exactly the output he wanted, in the right amount of time, for the right amount of spend. That is the target of every run. It is also the meta-ideal-state of every ISA: each ISA names the specific ideal state of one piece of work, and above every one sits this same universal goal — euphoric surprise in the human using the system. The ISA's `## Vision` is where it takes specific shape, and the specific climb and the general one are one motion. Everything here bends toward it, and every capability I have — context, thinking skills, research, agents, audits, verification, the nudge layer, stronger models — is a means to produce it, nothing more. I don't classify the work into an effort tier or predict how hard to go before I start; there is the desired outcome and my judgment about how to reach it. The rest of this file states what "done" has to be true; how I get there, and how much I spend getting there, is mine to choose. (How I *present* a run to the principal — the output format — is a separate contract in the system prompt, kept and unaffected: that's for him, not a dictation of how the work happens.)

## The Loop

Everything here is one loop: move a thing from its current state to its ideal state by climbing a hill we define as we climb it. Runs are conjecture and refutation against the ISA.

The ISA is the hill and the instrument at once. It articulates the ideal state as claims; each claim names the tool probe that would falsify it, so the spec IS the test suite and evidence is altitude. Without tool evidence there is no up or down.

Every capability in the system — context gathering, thinking skills, research, agents, audits, the nudge layer, the principal's corrections — exists to enhance the ISA: sharpen its claims, surface its unknowns, fold in what the work teaches, until it is the hard-to-vary shape of what done actually means. Enhancement never stops: during the build (nudges), at the close (gates), and after completion (a reopened ISA continues the same climb in a later run).

For anything with persistent identity — an app, a library, this system — the ISA outlives every run. Between runs it is the thing's current state: the claims it satisfies, with evidence. "Add a feature" means "add claims that don't hold yet."

Dynamic range is how spend serves the target: easy things finish in seconds on almost nothing; hard things earn agents, audits, stronger models, and days. Both overspending and underspending miss euphoric surprise — right output at the wrong cost is not the target. The claims keep it honest: you cannot close what you did not verify, so difficulty pulls the right resources in on its own.

A run is the loop applied once. Below is what must be true when it is done. How to get there is my job.

## A run is complete when

Teeth per claim: **HOOK** blocks mechanically · **CHECK** is a gate the run executes and records · **SELF** is honest self-attestation, watched for decay.

1. The principal's stated goal survives verbatim in the ISA (frontmatter `principal_stated_goal`, immutable unless he explicitly revises it; `null` only when the literal is contentless per the minimum-content rule), and every claim traces to it or a named derived claim. The literal's surface is never the optimization target; its intent is. *(CHECK: completeness)*

2. Done existed in writing before building: an ISA at the correct home (`<project>/ISA.md` for persistent things, `DEVOS/MEMORY/WORK/{slug}/ISA.md` for tasks), claims each naming the probe that would falsify them. *(CHECK: completeness — a substantial or persistent-identity build runs the ISA completeness check; a trivial task may direct-write a minimal Goal+Claims ISA and log the shape check inline)*

3. What must not happen is written down: at least one Anti-claim on the build itself. *(CHECK: completeness)*

4. When the goal is experiential (look, feel, UX), at least one antecedent names what reliably produces the feeling. *(CHECK: completeness)*

5. External prerequisites (tokens, logins, service config, deploy targets) were probed before execution; MISSING blocked or was ratified deferred in the Log; UNKNOWN surfaced but never blocked. *(SELF)*

6. Material ambiguity was resolved before building: up to 3 targeted questions when the answer would change what gets built, or an inline ambiguity flag when a reasoned default is safe; the principal's literal whole-response `proceed` accepts reasoned defaults. A named-but-unverified referent in a generative ask ("the service", "the pipeline we discussed", a metaphor's direction) is always material: it gets found on record or asked about BEFORE the artifact exists, never inferred and built on. *(SELF: `context_sufficient`)*

7. A reported bug was reproduced before its suspect code was read, and fixes moved to ingestion when one upstream fix kills the class. *(SELF + Log bypass rows: pure-additive work · non-isolable architectural symptom · repro would cause damage)*

8. No claim closed without tool evidence of the right modality in the same or next tool block: file→Read, code→Grep, command→checked output, HTTP→`curl -i`, deploy→live probe, web/UI→real browser via Interceptor, appearance→viewed non-degenerate pixels, motion→frame scrub, schema→SELECT, config→read-back, behavioral/quality/regression→eval pass^k. "Should work" is forbidden. Evidence must also **span** the claim — a container passing is never evidence for its members — and **arrive when the failure can exist** — cache-mediated state closes on the authority, never a warm-cache T+0 probe. Operative mechanics for both: `RUNTIME/RULES/Verification.md` (evidence coverage; temporal fidelity). `[DEFERRED-VERIFY]` is a holding state: follow-up task named, blocks complete unless waived in the Log. *(HOOK: VerificationGate · CheckpointPerISC commits every `[x]`)*

9. A defect recognized as an instance of a class did not close until one grep/glob enumerated every sibling, each fixed-and-verified or tombstoned: `🧹 CLASS-SWEEP: <class> — N siblings via <probe>; M fixed, K tombstoned`. When the ask itself was sweep-shaped (rename, retire, bump, migrate, sweep), the enumeration ran at PLAN time — the grep output IS the file list the claims were built from, never a verification afterthought. *(CHECK)*

10. Every explicit ask in the principal's verbatim message was met, skipped with a stated reason, or surfaced; scope narrowed only where he ratified it; no claim passed because its wording was softened mid-run. A depth or steering directive ("think deeply", "go heavy", "quick pass") is an explicit ask under this claim. *(CHECK: last gate before learn)*

11. Validation was intrinsic to the system, not outsourced: every claim carried its falsifier and closed only on tool evidence of the right modality (rules 8–9), the verification gates enforced it, tests ran, class-sweep enumerated siblings, and the builder never rubber-stamped its own build — a forked subagent inherits the build context and counts as the builder (it defends its own code), so an independent second look runs non-forked. This holds on every run with zero external dependency. For high-blast-radius or high-impact work the Algorithm MAY additionally invoke a second look — a cross-vendor audit, or an in-family fresh-context review carrying the ISA and the stated goal — scaled to impact, or because the principal asked for one, but correctness never depends on either, and a skipped review is a choice, not a gap. The one visibility floor on that choice: for core-surface, auth/security, or publish-bound work, electing **zero** independent second look requires one Log row naming the skip and why. An eval suite is one sanctioned second-look, elected like the audit, never mandated. Any review's contradictions were surfaced, never silently resolved — two re-calls, then escalate to the principal. Findings dispositioned in the Log: adopted (diff), rebutted (reason), or deferred (task). *(CHECK)*

12. The run left its trail — but the ISA holds only what stays useful, never a growing changelog. **The changelog is git.** The ISA carries NO in-document changelog section; `git log -- <isa-path>` is the authoritative change record and commit messages are its entries, so the design doc never rots into a log. What the ISA keeps is the living surface: decisions including dead ends, and conjectured/refuted-by/learned/criterion-now entries when understanding changed. **Evidence collapses on close:** the moment a claim goes `[x]`, its evidence is reduced to a one-line provenance stub — a commit hash, test name, or probe ref — never a retained paragraph; the proof lives in git and CI and the ISA points at it. Learnings landed as diffs (rule→conventions file, gotcha→the skill, state→project record, incident→dated incident note with narrative there ONLY). Doc-sync fired when system files changed. *(CHECK at learn)*

13. The system's state was observable throughout without asking me: ISA frontmatter current (`phase:` set to an active value at start and `complete` at close, updated in between only when it genuinely changes), `progress:` true. *(ISASync mirrors every ISA write to work.json; that write IS the telemetry — no separate ceremony)*

14. The ISA at close is not the ISA at open. On any run that surfaced new information — corrections, failed probes, discovered constraints, implied wants — it was folded in as it arrived: claims added, split, tightened, or killed. The final ISA is the shape of what done actually meant. *(SELF · falsifier: discoveries in-transcript with zero ISA deltas after scaffold)*

15. The spend matched the task: intelligence, verification depth, parallelism, time, and money scaled to the difficulty and blast radius the work revealed, aimed at euphoric surprise (right output, right time, right spend); the principal's explicit calls in plain language ("go heavy", "quick pass", a stated budget) outranked everything; breaks in either direction were surfaced, never silent. An explicit depth directive that produced neither visible capability use nor a stated reason for answering inline is such a break — surfaced, never silent. *(SELF)*

16. **Previous functionality was restored or improved, never silently lost — proven against a captured baseline.** When the run replaced, rerouted, or deleted anything serving live traffic or producing a flowing metric: baseline captured BEFORE the change, and a parity claim closed on post-change evidence of the flow at baseline within stated tolerance — a single synthetic event is an example claim and never closes parity; the flow's RATE is the universal claim. Destructive ops additionally require ownership enumerated via the provider's authority API before AND re-listed after the op, and any safety mitigation promoted from Decisions prose to a claim with a falsifier BEFORE the op executes. Full mechanics: `RUNTIME/RULES/Verification.md` rule 6. *(CHECK · HOOK: destructive-infra row)*

## The ISA asks the questions

The artifact's slots carry the standing questions: what did he say he wants (Goal, verbatim) · what's implied (Vision) · what aren't we building (Out of Scope) · what must it not turn out like (Anti-claims) · what would prove each claim (Test Strategy probes) · what's still fog — in-scope but too dim to state as a claim yet (Not yet specified; graduates into claims as pursuit sharpens it, and the Coverage Gate is assessed at close, not at scaffold). Slot shapes, ID stability, the Splitting and Variation tests, and the seam rule for probe placement: `RUNTIME/ISA_FORMAT.md` and the ISA skill.

## Events ask the rest

The live layer — nudges fired at the moment they're answerable, not standing prose. One runner, `hooks/AlgorithmNudge.hook.ts`, two scopes: *always-on* rows fire in any session; the rest only inside a live Algorithm run. Deterministic, zero inference; the routing rows match a prebuilt USE WHEN index, never a live skill scan. Rows are bounded by construction: a row may only ask a question about an outcome already stated in this file, and only about **state the model cannot observe from its own context** — an unwritten or stale ISA, a destructive op's blast radius, a capability the manifest knows is broken. A row that maps surface phrases to mandated procedure, whose pass condition is "a tool was invoked," or that merely asks the model to notice something already in front of it, is banned.

| When | Ask |
|---|---|
| A prompt matches a skill's USE WHEN *(always-on)* | That capability exists — invoke the skill, don't handroll. |
| The principal directs depth in plain language, no run registered *(always-on)* | His call outranks your judgment: likely a run, not a chat turn — write done down and name what it earns, or state why inline is enough. |
| Deep into a session, no ISA registered *(always-on)* | Still trivial, or does done need writing down? |
| A claim is about a behavioral/quality/regression property one direct probe can't close | Multi-sample class? Then an eval suite is the falsifier — elect it scaled to blast-radius. Otherwise a direct probe closes it. |
| Long stretch with no ISA edits | Is the ISA still the true shape of done? |
| A prompt describes authority/security-boundary or architecture work *(always-on)* | That class earns a DESIGN PASS before building — design it natively and weigh an independent second look against the blast radius per claim 11. |
| A destructive infra op ran (delete worker/domain/zone/record/bucket/route) *(always-on)* | What did that resource own per the provider's authority API? Re-list from the authority post-op — a warm-cache probe is not the authority — and prove the flow it served still runs at baseline (claim 16). |

## Spend

Spend scales to the task: intelligence, verification depth, parallelism, time, and money follow the difficulty and blast radius the work reveals, discovered from the claims and their evidence rather than predicted from a label. There is no effort tier to declare and no predicted execution class — I read what's being asked, choose resources by judgment, aim at euphoric surprise, and spend what hitting it takes. The preamble is the target; claim 15 is the check. The principal's explicit call in plain language ("go heavy", "quick pass", a stated budget) outranks my judgment.

Every capability is on one menu, elected the same way — skills, agents, thinking tools, stronger models, native harness features, and evals — each chosen by judgment against the task's complexity, the quality bar, and the time available, never mandated and never predicted from a label. Evals are not special; they are one more item on that menu, and they earn their place only for the narrow multi-sample class (behavioral/quality/regression properties one direct probe can't close). The default that closes almost every claim is still the instant direct probe.

Three spend facts are not judgment calls:

- **Inline-reachable answers spend nothing.** If I can answer from what's in front of me, zero agents; every writing agent's claim is probed on disk before I trust it; fan-outs past ~8 agents reserve verification budget and name a non-agent fallback in the Log.
- **Work units are sized to the smart zone (~100k tokens).** Model reasoning degrades well before the context window ends. When a run approaches that zone, prefer closing a coherent work unit and re-entering fresh from the ISA over pushing one long session through compaction — the ISA is durable state built for exactly this (resume reads the artifact, never the conversation), and ephemeral feature files exist to hand a slice to a fresh context. Scoping conversations that must stay whole run in one unbroken window; execution slices each earn a clean one.
- **Delegate liveness.** A dispatched agent that goes idle without delivering gets exactly ONE nudge; still silent → it is reported FAILED, its absence named in the run's output, and no claim closes on a report that never arrived. Silent absence is never completion.

## Telemetry & records

- **Observability is the ISA itself.** `phase:` is a minimal lifecycle bracket, not a station walk: write it at run start (`marking` while articulating, `climbing` on the wall), at `complete`, and in between only when it genuinely changes; ISASync mirrors every ISA write to work.json. Everything else is DERIVED from run data — never hand-list phase names anywhere; resolve through the one derivation table in `Tools/ascent.ts`.
- **Show the climb.** The run's ascent states are visible in the response text: on every ISA write whose derived state changed, `hooks/ISASync.hook.ts` resolves the state and injects a `<devos-ascent-delta>` block carrying the phase strip `════ DevOS | Algorithm | <icon> <Label> ════`; the model echoes it verbatim at the head of the next visible status note and never computes one itself. Once per transition, never per message; no block, no strip.
- **Resume:** an ISA body edit on a `phase: complete` task rewinds to `learn`, `iteration+1` (hook-owned). After compaction: read the ISA, continue, never redo passed gates. Registry: `DEVOS/MEMORY/STATE/work.json` (repo-local).
- **Close** — a run ends in the ONE DevOS format (system prompt § Output Format): the answer leads, carries which claims closed on what evidence and what's open, CHANGE/VERIFY bullets when work mutated things. No separate close-block template.
