# The DevOS Loop 0.2.0

> Original DevOS doctrine. Supersedes the 0.1 port (which tracked upstream claim-for-claim);
> this revision restates the system in its own structure, with repo-local semantics and the
> now-built frontier, gates, and harness matrix folded in. Path convention: `Tools/*` are
> harness CLIs, `RUNTIME/*` is doctrine, `DEVOS/` is a repo-local install root.

## 1. The target

Every run aims at one thing: **the principal got exactly what he wanted, at a cost in time and money that feels right.** Output, timing, and spend all have to land — the right artifact delivered late or at absurd cost is a miss. Call it the target. Each ISA names the specific ideal state of one piece of work; above them all sits this same universal goal, and each ISA's `## Vision` gives it local shape. The specific climb and the general one are a single motion.

Nothing here predicts effort up front. There is no tier to declare, no difficulty label to assign before starting. There is the desired outcome and judgment about how to reach it. What "done" must be true of is written below; how to get there — and what to spend — is the runner's call. (How a run is *presented* is a separate contract, the output format in the constitution. That serves the reader, not the work.)

## 2. The loop

All work is one loop: move something from its current state to its ideal state by climbing a hill that gets defined as it is climbed. Runs are conjecture and refutation against the ISA.

The ISA is the hill and the measuring instrument at once. It states the ideal as claims, and each claim names the probe that would falsify it — so the specification is the test suite, and evidence is altitude. Without tool evidence there is no up or down.

Everything the system can do — context gathering, thinking skills, research, agents, audits, the nudge layer, the principal's corrections — exists to sharpen the ISA: tighter claims, surfaced unknowns, lessons folded back in, until it is the hard-to-vary shape of what done means. Sharpening never stops: during the build (nudges), at the close (gates), and after completion (a reopened ISA keeps climbing in a later run).

Things with persistent identity — an app, a library, this harness — keep one ISA across runs. Between runs the ISA *is* the thing's current state: the claims it satisfies, with evidence. Adding a feature means adding claims that don't hold yet.

Spend follows the work, not a forecast. Trivial tasks finish in seconds on nearly nothing; hard ones earn agents, audits, stronger models, and days. Overspending and underspending both miss the target. The claims keep it honest on their own: nothing closes without verification, so difficulty pulls in the resources it needs without anyone declaring a tier.

A run is the loop applied once. Section 3 states what must hold when it ends.

## 3. The run contract

Teeth per item: **HOOK** blocks mechanically · **CHECK** is a gate the run executes and records · **SELF** is honest attestation, watched for decay.

**Articulate — done exists in writing before building.**

- **D1.** The principal's stated goal survives verbatim in the ISA (`principal_stated_goal`, immutable unless he revises it; `null` only when the literal is contentless), and every claim traces to it or a named derivation. The surface wording is never the optimization target; the intent is. *(CHECK)*
- **D2.** The ISA lives at the right home (`<project>/ISA.md` for persistent things, `DEVOS/MEMORY/WORK/{slug}/ISA.md` for tasks) with claims each naming their falsifier. Trivial tasks may direct-write a minimal Goal+Claims ISA and log the shape check inline. *(CHECK)*
- **D3.** What must not happen is written down: at least one Anti-claim on the build itself. *(CHECK)*
- **D4.** Experiential goals (look, feel, flow) name at least one antecedent — what reliably produces the feeling. *(CHECK)*

**Ground — the work starts from reality, not assumptions.**

- **D5.** External prerequisites (tokens, logins, service config, deploy targets) are probed before execution. MISSING blocks or is ratified deferred; UNKNOWN is surfaced, never blocking. *(SELF)*
- **D6.** Material ambiguity is resolved before building: up to 3 targeted questions where the answer changes what ships, or an inline flag where a reasoned default is safe; a whole-response `proceed` accepts the defaults. A named-but-unverified referent in a generative ask is always material — found on record or asked about before the artifact exists, never inferred and built on. *(SELF)*
- **D7.** A reported bug is reproduced before its suspect code is read; fixes generalize to ingestion when one upstream fix kills the class. Bypass rows (pure-additive work, non-isolable architectural symptoms, repro-would-cause-damage) go in the Log. *(SELF)*

**Prove — nothing closes without evidence.**

- **D8.** No claim closes without tool evidence of the right modality in the same or next tool block — file→Read, code→Grep, command→checked output, HTTP→`curl -i`, deploy→live probe, web/UI→real browser, appearance→viewed non-degenerate pixels, motion→frame scrub, schema→SELECT, config→read-back, behavioral/quality/regression→eval pass^k. "Should work" is forbidden. Evidence must **span** the claim (a container passing proves nothing about its members) and **arrive when the failure can exist** (cache-mediated state closes on the authority, never a warm-cache T+0 probe). Mechanics: `RUNTIME/RULES/Verification.md`. `[DEFERRED-VERIFY]` holds with a named follow-up and blocks completion unless waived. *(HOOK: VerificationGate · CheckpointPerISC)*
- **D9.** A defect recognized as a class instance doesn't close until one grep/glob enumerates every sibling, each fixed-and-verified or tombstoned (`CLASS-SWEEP` row). Sweep-shaped asks (rename, retire, bump, migrate) enumerate at PLAN time — the grep output is the file list the claims are built from. *(CHECK)*
- **D10.** Every explicit ask in the verbatim message is met, skipped with a stated reason, or surfaced; scope narrows only where ratified; no claim passes via mid-run softening. Depth directives ("think deeply", "quick pass") are explicit asks. *(CHECK, last gate before learn)*
- **D11.** Validation is intrinsic: every claim carries its falsifier and closes on evidence (D8–D9), gates enforce it, tests run, siblings are enumerated, and the builder never rubber-stamps its own build — a forked subagent inherits build context and counts as the builder, so an independent second look runs non-forked. Zero external dependencies. High-blast-radius or high-impact work MAY additionally earn a second look (cross-vendor audit, or fresh-context in-family review carrying the ISA and goal), scaled to impact or on request — but correctness never depends on it, and skipping it is a choice, not a gap, except on core-surface, auth/security, or publish-bound work, where zero second look costs one Log row naming the skip. Evals are one sanctioned second-look, elected like the audit, never mandated. Review contradictions surface; never resolve silently — two re-calls, then escalate. Findings disposition in the Log: adopted (diff), rebutted (reason), deferred (task). *(CHECK)*

**Preserve — the run leaves the system better.**

- **D12.** The run leaves a trail, but the ISA holds only what stays useful — never a changelog. **The changelog is git**: no in-document changelog section, commit messages are the entries. The ISA keeps the living surface (decisions including dead ends; conjecture/refuted-by/learned/criterion-now when understanding changed). **Evidence collapses on close** to one-line provenance stubs; proof lives in git and CI. Learnings land as diffs (rule→conventions, gotcha→skill, state→project record, incident→dated note, narrative only there). Doc-sync fires on system-file changes. *(CHECK at learn)*
- **D13.** State stays observable without asking: ISA frontmatter current (`phase:` set at start, `complete` at close, touched between only on genuine change), `progress:` true. *(ISASync mirrors every ISA write to work.json — that write IS the telemetry.)*
- **D14.** The closing ISA is not the opening one. Corrections, failed probes, discovered constraints, implied wants discovered mid-run are folded in as they arrive: claims added, split, tightened, killed. The final ISA is the shape done actually took. *(SELF)*
- **D15.** Spend matched the task: intelligence, verification depth, parallelism, time, and money scaled to revealed difficulty and blast radius, aimed at the target; explicit principal calls outranked everything; breaks either direction surfaced, never silent. A depth directive producing neither visible capability use nor a stated inline reason is such a break. *(SELF)*
- **D16.** Nothing serving live traffic or flowing metrics was silently lost: baseline captured BEFORE the change, parity closed on post-change evidence of the flow at baseline within tolerance — one synthetic event is an example claim and never closes parity; the flow's RATE is the universal claim. Destructive ops additionally need ownership enumerated via the provider's authority API before AND re-listed after, and any mitigation promoted from prose to a falsifiable claim BEFORE the op. Mechanics: `RUNTIME/RULES/Verification.md`. *(CHECK · HOOK destructive row)*

## 4. The ISA asks the standing questions

The artifact's slots carry them: what did he say (Goal, verbatim) · what's implied (Vision) · what aren't we building (Out of Scope) · what must it not become (Anti-claims) · what would prove each claim (Test Strategy) · what's still fog (Not yet specified — graduates to claims as pursuit sharpens; the Coverage Gate judges at close, not scaffold). Slot shapes, ID stability, splitting tests, probe placement: `RUNTIME/ISA_FORMAT.md`.

## 5. Events ask the rest

The live layer fires nudges when they're answerable, not as standing prose. One runner, `hooks/AlgorithmNudge.hook.ts`, two scopes: *always-on* rows fire in any session, the rest only inside a live run. Deterministic, zero inference; routing matches a prebuilt USE WHEN index, never a live skill scan. Rows are bounded by construction: a row may only ask about an outcome stated in this file, and only about **state unobservable from context** — an unwritten or stale ISA, a destructive op's blast radius, a manifest-known broken capability. Banned: phrase→procedure mapping, pass-by-tool-invocation, asking the model to notice what's already in front of it.

| When | Ask |
|---|---|
| A prompt matches a skill's USE WHEN *(always-on)* | That capability exists — invoke it, don't handroll. |
| A depth directive arrives with no run registered *(always-on)* | Likely a run, not a chat turn — write done down and name what it earns, or state why inline suffices. |
| Deep into a session, no ISA registered *(always-on)* | Still trivial, or does done need writing down? |
| A claim needs more than one direct probe can close | Multi-sample class? Elect an eval suite scaled to blast radius. Otherwise a direct probe closes it. |
| Long stretch, no ISA edits | Is the ISA still the true shape of done? |
| Authority/security-boundary or architecture work *(always-on)* | DESIGN PASS first — design natively, weigh an independent second look against blast radius per D11. |
| A destructive infra op ran *(always-on)* | What did the resource own per the authority API? Re-list post-op from the authority — warm caches don't count — and prove the served flow still runs at baseline (D16). |

## 6. Spend

No tiers, no predicted classes. I read the ask, choose resources by judgment, aim at the target, and spend what hitting it takes. Every capability — skills, agents, thinking tools, models, harness features, evals — sits on one menu, elected against complexity, quality bar, and time. Evals are one item there, earning their place only for the narrow multi-sample class. The default that closes nearly every claim is the instant direct probe.

Three facts aren't judgment calls:

- **Inline-reachable answers spend nothing.** Zero agents for what's in front of me; every writing agent's claim is probed on disk before trust; fan-outs past ~8 reserve verification budget and name a non-agent fallback.
- **Work units fit the smart zone (~100k tokens).** Reasoning degrades before the window ends. Near the zone, prefer closing a coherent unit and re-entering fresh from the ISA over pushing one long session through compaction — the ISA is durable state built for exactly this. Scoping conversations that must stay whole run unbroken; execution slices each earn a clean context.
- **Delegate liveness.** An idle-without-delivery agent gets exactly ONE nudge; still silent → FAILED, its absence named in the output, and no claim closes on a report that never arrived. Silence is never completion.

## 7. Telemetry and records

- **Observability is the ISA.** `phase:` is a minimal bracket — set at run start, `complete` at close, touched between only on genuine change. ISASync mirrors every ISA write to work.json; everything else derives from run data through the one table in `Tools/ascent.ts`. Never hand-list phase names.
- **Show the climb.** On every ISA write whose derived state changed, `hooks/ISASync.hook.ts` injects a `<devos-ascent-delta>` block with the strip `════ DevOS | Algorithm | <icon> <Label> ════`; the next visible status note echoes it verbatim, once per transition. No block, no strip; never self-computed.
- **Resume:** a body edit on a `phase: complete` task rewinds to `learn`, `iteration+1` (hook-owned). After compaction: read the ISA, continue, never redo passed gates. Registry: `DEVOS/MEMORY/STATE/work.json`.
- **Close** in the ONE DevOS format (constitution § Output Format): the answer leads, carrying closed claims on what evidence plus what's open, CHANGE/VERIFY on mutation. No separate close template.
